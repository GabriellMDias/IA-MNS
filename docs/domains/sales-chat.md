# Sankhya Sales Capability

[Corporate agent](corporate-agent.md) · [Project plan](../project/implementation-plan.md) · [Setup](../setup.md) · [Architecture decision](../adr/0018-bound-natural-language-sales-to-a-read-only-query-capability.md)

## Scope and acceptance

The first business capability of the IA-MNS corporate agent lets an authorized MNS sales reader ask questions in Portuguese about confirmed Sankhya sales, receive real aggregates, and continue with related questions. Example: “Quanto vendi de maçã por mês nos últimos 3 meses?” followed by “E comparado ao mesmo período do ano passado?”. Generic monetary questions use VLRLIQUIDO. Literal phrase matching against TGFPRO descriptions is sufficient for this MVP.

Acceptance requires an executable API/web workflow, validated interpretation, deterministic calculations, explicit missing configuration and provider errors, contextual comparisons, useful suggestions, no arbitrary SQL, and no ERP writes. Actual ERP reconciliation and live model interpretation additionally require the credentials tracked in the [human checklist](../project/human-actions.md#ph-08). Synthetic tests do not establish the business accuracy of a real database.

Only net value, quantity, weight, totals, monthly breakdown, product breakdown, and comparisons with the prior year or immediately preceding equal-length period are supported. Other processes, returns as a separate report, customer/seller/company filters, automation, exports, login, and deployment are outside this capability. Durable conversation history belongs to the agent module. A capability user reads all companies represented by this ERP reference; no tenant or per-company isolation is implied.

## Sales semantics

The canonical executable reference is [query.ts](../../apps/api/src/features/sales/query.ts), transcribed from the owner's SQL on 2026-10-01. Preserve its complete DISTINCT projection, required inner joins, optional joins, adjusted-price precedence, and exclusions. In particular:

- Confirmed notes require `CAB.STATUSNOTA = 'L'`, product usage `M` or `R`, excluded operation codes `1002, 915, 9599, 905, 575, 930, 568, 515, 450, 460, 1006, 1008`, and excluded group `85007003`.
- The final reference restricts computed `TIPMOV = 'V'`. The computed movement maps bonus sales to `B`, so bonus sales and returns are excluded. Do not subtract returns from the final totals merely because signed return measures exist inside the CTE.
- VLRLIQUIDO uses nonzero `AJI.AD_VLRTOTFIN`, then nonzero `ITE.AD_TOTALAJUSTADO`, then `ITE.VLRTOT - ITE.VLRDESC`, subtracts `ITE.AD_VLRTOTALBONIFI`, and applies the reference movement sign.
- Quantity uses QTDNEG and is grouped separately by CODVOL; different units never share a total. Monetary values assume BRL, which must be confirmed by the owner. Weight uses QTDNEG × PESOLIQ. The ERP weight unit has not been verified; the UI does not label it kilograms. Missing or nonpositive PESOLIQ produces a warning without changing the reference calculation.
- Dates use DTNEG. The inclusive user end date becomes an exclusive next-day boundary so timestamps throughout that day are included. The supplied BETWEEN query needs its end bind to include that same day for reconciliation.
- Product matching is a literal, case/accent-insensitive phrase bounded by non-alphanumeric characters, with whitespace normalized. Regex metacharacters are escaped before binding. A product word cannot match the prefix of an unrelated product word. The answer lists products with sales in either requested period, not all catalog products without sales. Generic all-product queries omit the match list.

Join fan-out and duplicate collapse follow the owner's reference. This may retain duplicate effects from multiple adjustment/origin/lot matches; removing or choosing an adjustment requires reconciliation and a separate rule. Product predicates run before DISTINCT, and the lot subquery considers only controls belonging to eligible items; all lot matches for those controls remain eligible. This prunes irrelevant work without choosing a lot or adjustment or changing the projected grain. No schema, index, grant, migration, or object is created in Sankhya.

## Interpretation and computation

The server uses the OpenAI Node SDK Responses API with one forced strict `plan_sales_query` function call. A plan can request a bounded query, select a clarification category, or reject unsupported scope. All public messages, including clarification and rejection, are application-authored; model text never becomes a public sales answer. The model cannot supply arbitrary clarification text or monetary claims. Requests that require unsupported scope are rejected rather than partially answered. The model receives the current Sao Paulo date, recent questions, and the server's last successful filters. Missing periods require clarification. “Last N months” defaults to the last N completed calendar months; including the current month must be explicit. This month/year ends today; last N days includes today and N-1 preceding dates. Weight requests, including kg, select weight rather than quantity grouped by KG; no unverified weight conversion is implied. Follow-ups, including identifying considered products, preserve prior filters unless explicitly changed.

All tool output is checked at the provider boundary and then validated by the application. Both current and derived comparison date ranges are real calendar dates from 2000 onward, at most 366 inclusive days, and never future dates. Descriptions have 2–80 characters. Each period, including monthly zero filling, is limited to 500 aggregate rows and 100 matched products; the combined comparison list has at most 200 unique products. Excessive results fail visibly without returning incomplete totals. Empty aggregates retain no synthetic zero row. There is no SQL tool, generated SQL, agent delegation, or vector database.

Current and comparison queries share one Oracle read-only transaction and snapshot. Decimal strings are converted to 50-digit decimal arithmetic for totals and percentage changes. Monthly results fill missing months with zero for known units. A zero comparison base has an undefined percentage, not infinity. Prior-year leap days clamp to February 28. The previous-period comparison uses an equal number of days, rather than assuming whole months. Replies, tables, and suggestions are built from validated results; sales numbers are not authored by the model.

## Identity, privacy, and context

Sales execution requires sales:read under Orion's verified bearer principal, or explicit local access. The [agent](corporate-agent.md#persistent-conversations-and-context) owns durable conversation identity, concurrency, context and history. Sales context stores its last validated query and a bounded sales question/clarification window; ERP result rows are not model context. Failed turns preserve prior filters. The legacy sales endpoints keep their original 30-minute/12-question in-memory semantics for compatibility, while the product exclusively uses durable agent endpoints.

The explicit `IA_MNS_LOCAL_ACCESS=true` mode is for a single developer on loopback only. Configuration rejects it in production or on a public listener; requests also require a loopback client/host, a local browser origin, and the custom client header, and reject cross-site fetches. It grants the local developer the sales-read capability. Do not expose the development Vite proxy or tunnel it; local mode is not a shared environment authentication system. Production requires configured providers and a trusted verifier at startup. A concrete issuer/login remains conditional under PJ-05.

Sales, questions, filters, and product descriptions are CONFIDENTIAL. Credentials are RESTRICTED. The browser holds token/context/results in memory and clears them on credential changes; only the light/dark theme preference uses browser storage. Protected responses use no-store. New conversation preserves history; explicit deletion removes persisted conversation/context/turns. Model requests use `store:false`, which does not establish zero provider retention or account-specific policy. Only questions and filter context go to OpenAI, never sales rows, prices, customer names, credentials, or raw schema. Users must avoid putting unrelated confidential information or credentials in questions.

Provider exceptions produce safe public error envelopes plus one correlated, allowlisted diagnostic, including the provider/stage and bounded public Oracle/OpenAI error codes. Provider/stage remain internal and never include raw messages or configuration. Rollback/close failures remain provider failures and prevent returning an unverified success. No prompt, result, query binds, Oracle connect descriptor, or secret enters logs. Chat input is limited to 2,000 characters and 12 KB transport size; actor rate limit is 15 questions per minute. Model timeout is 20 seconds, Oracle round-trip timeout 45 seconds, pool wait 5 seconds, and execution deadline 90 seconds. Agent acceptance returns immediately and its browser polls actual progress. The legacy sales route overrides the foundation socket inactivity timeout to 95 seconds, while other routes retain their existing budget. Real ERP queries exceeded the original 10-second round-trip limit, so the bounded budgets now accommodate the measured workload. Limits are process-local, not a distributed quota.

## Local execution and external verification

Follow [setup](../setup.md#sales-chat) and the generated [configuration reference](../generated/configuration/api.md). Oracle node-oracledb 7 supports Oracle 12.1 in Thin mode; if an actual authentication/network feature requires Thick mode, configure a compatible Oracle Client directory. Client 19 or 21 supports this database version; newer clients are not automatically compatible with older servers ([driver compatibility matrix](https://node-oracledb.readthedocs.io/en/stable/user_guide/installation.html)). The account must have CREATE SESSION and SELECT only on the reference tables, with schema resolution supplied by the DBA. No login/provider or real ERP account is provisioned by this repository.

The 2026-10-01 read-only audit connected to Oracle 12.1.0.2 with Client 19.32 after the configured Client 11.2 failed with DPI-1050 and Thin mode failed with NJS-116. Nine structured-query scenarios matched the supplied SQL's aggregates in a shared read-only snapshot: monthly net value, month to date, rolling 30-day weight, quantity by unit, product breakdown, previous year, equal-length prior period, accent/case equivalence, and no matching sales. The complete 46-column reference projection also matched for the current three-month product scope. Returns and bonus movements were present in the source and excluded by the final sales filter. Actual HTTP injection with the real Oracle adapter passed annual comparison and empty-result handling using a controlled planner; this is not a live natural-language test.

The audit exposed unrelated description-prefix matches, a comparison product list exceeding the original cap, and Oracle work exceeding the original timeout. Word boundaries now exclude unrelated prefixes, both periods contribute to the product list, limits reject truncation, and eligible-control pruning reduces work while retaining the reference projection. Oracle response shape/numeric checks reject malformed results rather than inventing empty sales. Small fetch batches in this legacy Oracle/Thick stack produced an intermittent difference in one complete record, although database-side MINUS in both directions returned no differences and aggregates matched. Fetching the complete bounded result together matched every field; the adapter now aligns its fetch array size with each result cap. This workaround does not establish the precise driver/server cause, which remains a DBA investigation under PH-08.

No business totals, credentials, or connection descriptor are committed as evidence. The owner later configured a key manually and explicitly authorized reuse. Ten actual language requests, eight original-SQL reconciliations, and a real-browser sales query passed; see [live verification](../project/live-sales-verification.md). Synthetic tests remain distinct evidence. The supplied account also has broad write privileges, which the DBA must remove by providing a dedicated reader. Weight-unit and currency confirmation remain owner actions.

Boundary tests use the real OpenAI SDK with synthetic HTTP responses and Oracle connection doubles. API injection tests exercise actual Fastify authorization, context, validation, and error envelopes. Browser journeys exercise the generated SDK with intercepted synthetic sales responses, while the unavailable-configuration path reaches the real emitted API. These checks do not replace validation against Oracle 12.1 or a live model. Run the full [validation gate](../validation.md) before handoff. On the real ERP, compare at least an adjusted item, a bonus exclusion, a return exclusion, multiple adjustment joins, accented descriptions, mixed units, missing weight, month end, and both comparison periods against the reference. No verification operation writes ERP data.
