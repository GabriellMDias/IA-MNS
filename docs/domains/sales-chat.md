# Sales Capability

## Scope and acceptance

The first business capability of the IA-MNS corporate agent lets an authorized sales reader ask questions in Portuguese about the sales of MNS (Sankhya) and Pilar da Terra (VRMaster), receive real aggregates, and continue with related questions. The person chooses the source in the interface ([sources](#sources)). Example: “Quanto vendi de maçã por mês nos últimos 3 meses?” followed by “E comparado ao mesmo período do ano passado?”. Generic monetary questions use the source's monetary measure: VLRLIQUIDO in Sankhya, `valortotal` in VRMaster. Ordinary literal-description filters remain supported; [semantic product selections](#semantic-product-selections) add verified registration conditions without changing sales measures.

Acceptance requires an executable API/web workflow, validated interpretation, deterministic calculations, explicit missing configuration and provider errors, contextual comparisons, useful suggestions, no arbitrary SQL, and no ERP writes. Actual ERP reconciliation and live model interpretation additionally require the credentials tracked in the [human checklist](../project/human-actions.md#ph-08) ([PH-20](../project/human-actions.md#ph-20) for VRMaster). Synthetic tests do not establish the business accuracy of a real database.

Only net value, quantity, weight (Sankhya only), totals, monthly breakdown, product breakdown, and comparisons with the prior year or immediately preceding equal-length period are supported. Other processes, returns as a separate report, customer/seller/store transaction filters, margins, costs, taxes, automation, exports, login, and deployment are outside this capability. Current product cost centers, buyers and other enabled registration conditions come from the separate [product resolver](product-lookup.md), then restrict eligible sales. They are not sale-time buyer or transactional cost-center filters. Durable conversation history belongs to the agent module. A capability user reads every source and all companies represented by each reference; `sales:read` grants both sources and no tenant or per-company isolation is implied.

## Semantic product selections

The normal conversational sales path can now use the same verified resolver as product lookup. A user must hold both `sales:read` and `products:read`; existing administration grants them, without new automatic grants or authentication changes. Select one ERP in **Fonte**. Qualified product concepts and catalog conditions are resolved before sales, using the existing grounding, relationships, hierarchy expansion and ambiguity choices. Simple literal phrases retain their existing behavior; explicit description requests stay literal. Unavailable conditions do not become description guesses or overall totals. Unsupported sales/customer/seller/store/price/stock requests remain unsupported as a whole.

| Conversational scenario | Expected behavior |
| --- | --- |
| VR Master: `Quanto vendi de banana fruta no mês passado?` | Resolves the fresh-banana classification and exclusions, then calculates sales for the complete selection with the reference grain |
| VR Master: `Quanto vendi dos produtos do centro de custo SECOS em setembro de 2026?` | Product → current section → cost center membership restricts sales; no assumption of a cost center on sale rows |
| First `Quais produtos são banana fruta?`, complete any displayed choice, then `Quanto vendi desses produtos no mês passado?` | Explicitly reuses that source's completed selection; a lookup in another ERP or an unanswered choice asks for identification/confirmation |
| `Quanto vendi de banana fruta?`, then supply only the requested period | Retains the original semantic request, with no ERP sales query until the period and selection are complete |
| An ambiguous sales request, then a displayed numbered product option | The choice resumes sales with its saved period; no sales query precedes the choice |
| `E comparado ao mesmo período do ano passado?`, `E a quantidade vendida?`, or `Detalhe por produto` | Retains the same semantic scope; only the stated analytical fields change |
| `E de todos os produtos?`, or an unrelated new overall-sales request | Clears the semantic scope; a new request never silently inherits the last lookup |
| Sankhya: `Qual o valor vendido dos produtos com unidade alternativa KG em setembro de 2026?` | Uses verified indirect unit membership; duplicate alternate-unit rows do not duplicate sales |
| Select `Tudo` for a semantic request | Asks for one ERP; ordinary literal/all-product sales still query both separately |

The answer shows the applied semantic criteria and source. Selection uses the **current product registration**, including its current buyer/category, equally for the requested and comparison periods. It does not reconstruct historical assignments or switch the existing measure to another business calculation. Registration members with no eligible reference sales contribute zero; product counts and counts of sold products are different concepts. Breakdown and quantity-unit rules remain unchanged, including no VR Master weight measure.

The backend compiles complete key membership, never the first 200 displayed products. Semantic sales lists at most 100 sold products per period and warns when the list is incomplete; totals still cover all members. The 500-row aggregate cap still refuses an oversized detailed query rather than returning partial figures. Metadata/catalog/access validation and cancellation fail closed. A catalog-version change asks for identification again. No new ERP grants or writes are needed for already enabled dimensions.

## Sources

The agent interface offers a selector beside the message box with exactly `MNS (Sankhya)`, `Pilar da Terra (VR Master)` and `Tudo`; it starts at `MNS (Sankhya)`. The web keeps the choice in memory while the application is open, across conversations, and sends it with each turn as `source` (`sankhya`, `vrmaster` or `all`); a reload starts again from `MNS (Sankhya)` and nothing is stored as a preference. The API records the source with the turn ([agent](corporate-agent.md#persistent-conversations-and-context)). The selection replaces the conversational "Sankhya or VRMaster?" question decided on 2026-10-06, which was never implemented ([ADR-0027](../adr/0027-select-the-sales-source-in-the-interface-and-read-each-source-separately.md)).

- **The selection decides, never the text.** `MNS (Sankhya)` queries only Sankhya and `Pilar da Terra (VR Master)` only VRMaster. Source and company names in a message neither switch, add nor filter a source: the interpreter ignores them, the application drops a source name placed in a filter, and a message naming another source receives an application-authored notice that the selected source was used.
- **`Tudo` queries both, separately for ordinary sales.** The same literal/all-product analysis plan runs in both sources in parallel. The answer has one section per source with its provenance, status and own totals, and says that values are not summed. A semantic product scope asks for one ERP. No combined figure exists without a later product decision.
- **Failures stay attributed.** With `Tudo`, a source that is unavailable, not configured or too broad is reported in its section beside the other source's result, and the failure is logged with the turn; the turn fails only when both fail. With a single source, its failure fails the turn and leaves the conversation state unchanged.
- **Measures per source.** Net value and quantity exist in both sources; weight only in Sankhya. A weight question with VRMaster alone is answered as unavailable without querying it; with `Tudo`, the VRMaster section says the measure is unavailable.
- **Literal plans remain source-independent.** Changing the selector and asking a follow-up (for example "E em agosto?") reuses the ordinary active analysis in the newly selected source. Semantic plans keep their source-scoped selection; a selection from another ERP is never translated or silently removed.

The application layer runs the adapters through the source-neutral `SalesReader` port ([reader.ts](../../apps/api/src/features/sales/reader.ts)). The Oracle adapter knows only the Sankhya reference and the PostgreSQL adapter only the VRMaster reference; they share the port, the scope check of aggregate rows and the literal product-phrase matching ([product-match.ts](../../apps/api/src/features/sales/product-match.ts)), not SQL or connections.

## Sankhya sales semantics

The canonical executable reference is [query.ts](../../apps/api/src/features/sales/query.ts), transcribed from the owner's SQL on 2026-10-01. Preserve its complete DISTINCT projection, required inner joins, optional joins, adjusted-price precedence, and exclusions. In particular:

- Confirmed notes require `CAB.STATUSNOTA = 'L'`, product usage `M` or `R`, excluded operation codes `1002, 915, 9599, 905, 575, 930, 568, 515, 450, 460, 1006, 1008`, and excluded group `85007003`.
- The final reference restricts computed `TIPMOV = 'V'`. The computed movement maps bonus sales to `B`, so bonus sales and returns are excluded. Do not subtract returns from the final totals merely because signed return measures exist inside the CTE.
- VLRLIQUIDO uses nonzero `AJI.AD_VLRTOTFIN`, then nonzero `ITE.AD_TOTALAJUSTADO`, then `ITE.VLRTOT - ITE.VLRDESC`, subtracts `ITE.AD_VLRTOTALBONIFI`, and applies the reference movement sign.
- Quantity uses QTDNEG and is grouped separately by CODVOL; different units never share a total. Monetary values assume BRL, which must be confirmed by the owner. Weight uses QTDNEG × PESOLIQ. The ERP weight unit has not been verified; the UI does not label it kilograms. Missing or nonpositive PESOLIQ produces a warning without changing the reference calculation.
- Dates use DTNEG. The inclusive user end date becomes an exclusive next-day boundary so timestamps throughout that day are included. The supplied BETWEEN query needs its end bind to include that same day for reconciliation.
- Product matching is a literal, case/accent-insensitive phrase bounded by non-alphanumeric characters, with whitespace normalized. Regex metacharacters are escaped before binding. A product word cannot match the prefix of an unrelated product word. The answer lists products with sales in either requested period, not all catalog products without sales. Generic all-product queries omit the match list.

Join fan-out and duplicate collapse follow the owner's reference. This may retain duplicate effects from multiple adjustment/origin/lot matches; removing or choosing an adjustment requires reconciliation and a separate rule. Product predicates run before DISTINCT, and the lot subquery considers only controls belonging to eligible items; all lot matches for those controls remain eligible. This prunes irrelevant work without choosing a lot or adjustment or changing the projected grain. No schema, index, grant, migration, or object is created in Sankhya.

## VRMaster sales semantics

The canonical executable reference is [vrmaster-query.ts](../../apps/api/src/features/sales/vrmaster-query.ts), transcribed on 2026-10-07 from the owner's reference SQL ([PH-18](../project/human-actions.md#ph-18)), a PDT Connect dashboard query over `venda`.

- Sales are the rows of `public.venda` that survive the reference's joins: inner joins to `produto`, `loja`, the store's `fornecedor`, `produtoaliquota` for the product in the store's state, `aliquota`, and the product's level-1 `mercadologico`; left joins to `centrocusto` and `comprador`. Every join is preserved as supplied, including its cardinality, because dropping one could change which sales count. Only the columns IA-MNS reports are projected; the reference's cost, tax, margin and profit computations are not used.
- Every store counts. The reference's `venda.id_loja = ANY(:lojas)` parameter is omitted: its inner join to `loja` already admits exactly the sales of existing stores, so omitting the parameter equals passing every store.
- Dates use `venda.data`; the inclusive end date becomes an exclusive next-day boundary, as in the reference.
- Net value is the sum of `venda.valortotal` and is labeled "valor total". Quantity is the sum of `venda.quantidade` per `produto.id_tipoembalagem`, labeled by the packaging-type identifier because the packaging-type table is outside the reference and the account's grants; different types are never added. VRMaster has no reviewed weight.
- Product matching applies the shared literal phrase to `produto.descricaocompleta`: accented letters are translated before `upper()` so the match does not depend on the database's character classification, whitespace is collapsed, and the pattern is a bound value with its metacharacters escaped.
- Table names are schema-qualified (`public.`), so a role `search_path` cannot redirect them. Product labels are `id - descricaocompleta`.

Whether the reference's `calculos` step filters rows could not be read from the supplied excerpt; the transcription assumes it only derives columns. The [reconciliation](../project/human-actions.md#ph-20) compares IA-MNS with the full reference and must confirm or correct this.

## Interpretation and computation

The server uses the OpenAI Node SDK Responses API, through the structured-model port, with one forced strict `interpret_sales_message` function call. The interpretation reports a decision (analyze, clarify for genuine ambiguity, or reject unsupported scope), how the message relates to the conversation, and only what the message states; the application merges it into the structured conversation state, asks for missing information, and compiles a bounded query ([AI interpretation](../architecture/ai-interpretation.md)). All public messages, including clarification and rejection, are application-authored; model text never becomes a public sales answer. The model cannot supply arbitrary clarification text or monetary claims. Requests that require unsupported scope are rejected rather than partially answered. The model receives the current Sao Paulo date, recent sales exchanges with the application's replies, and the structured state (last executed filters and any unanswered request). Missing periods require clarification; a later reply that supplies only the period completes the request it answers. The model names the period form and the application computes its dates; periods that have not started are asked again and periods over 366 days explain the limit. “Last N months” defaults to the last N completed calendar months; including the current month must be explicit. This month/year ends today; last N days includes today and N-1 preceding dates. Weight requests, including kg, select weight rather than quantity grouped by KG; no unverified weight conversion is implied. Follow-ups, including identifying considered products, preserve prior filters unless explicitly changed. The interpretation never chooses the source: since interpreter `sales-interpreter/2026-10-07.1`, names of the sources, companies or systems (MNS, Sankhya, Pilar da Terra, VR Master) are neither filters nor unsupported, while a store filter remains unsupported.

All tool output is checked at the provider boundary and then validated by the application. Both current and derived comparison date ranges are real calendar dates from 2000 onward, at most 366 inclusive days, and never future dates. Descriptions have 2–80 characters. Each period, including monthly zero filling, is limited to 500 aggregate rows and 100 matched products; the combined comparison list has at most 200 unique products. Excessive results fail visibly without returning incomplete totals. Empty aggregates retain no synthetic zero row. There is no SQL tool, generated SQL, agent delegation, or vector database.

Current and comparison queries of one source share one read-only transaction and snapshot: Oracle `SET TRANSACTION READ ONLY`, PostgreSQL `BEGIN ISOLATION LEVEL REPEATABLE READ READ ONLY`, always rolled back. Decimal strings are converted to 50-digit decimal arithmetic for totals and percentage changes. Monthly results fill missing months with zero for known units. A zero comparison base has an undefined percentage, not infinity. Prior-year leap days clamp to February 28. The previous-period comparison uses an equal number of days, rather than assuming whole months. Replies, tables, and suggestions are built from validated results; sales numbers are not authored by the model.

## Identity, privacy, and context

Sales execution requires sales:read under Orion's verified bearer principal, or explicit local access. The [agent](corporate-agent.md#persistent-conversations-and-context) owns durable conversation identity, concurrency, context and history. Sales context stores structured conversation state (last executed plan and query, unanswered request, bounded exchanges with application-authored replies); ERP result rows are not model context. The context does not depend on the source. The legacy `/sales/chat` endpoint always uses Sankhya. Failed turns preserve prior filters. The legacy sales endpoints keep their original 30-minute/12-question in-memory semantics for compatibility, while the product exclusively uses durable agent endpoints.

The explicit `IA_MNS_LOCAL_ACCESS=true` mode is for a single developer on loopback only. Configuration rejects it in production or on a public listener; requests also require a loopback client/host, a local browser origin, and the custom client header, and reject cross-site fetches. It grants the local developer the sales-read capability. Do not expose the development Vite proxy or tunnel it; local mode is not a shared environment authentication system. Production requires configured providers and a trusted verifier at startup. A concrete issuer/login remains conditional under PJ-05.

Sales, questions, filters, and product descriptions are CONFIDENTIAL. Credentials are RESTRICTED. The browser holds token/context/results in memory and clears them on credential changes; only the light/dark theme preference uses browser storage. Protected responses use no-store. New conversation preserves history; explicit deletion removes persisted conversation/context/turns. Model requests use `store:false`, which does not establish zero provider retention or account-specific policy. Only questions and filter context go to OpenAI, never sales rows, prices, customer names, credentials, or raw schema. Users must avoid putting unrelated confidential information or credentials in questions.

Provider exceptions produce safe public error envelopes plus one correlated, allowlisted diagnostic, including the provider/stage and bounded public Oracle/OpenAI error codes. Provider/stage remain internal and never include raw messages or configuration. Rollback/close failures remain provider failures and prevent returning an unverified success. No prompt, result, query binds, Oracle connect descriptor, VRMaster host or account, or secret enters logs. Chat input is limited to 2,000 characters and 12 KB transport size; actor rate limit is 15 questions per minute. Model timeout is 20 seconds, Oracle round-trip timeout 45 seconds, pool wait 5 seconds, and execution deadline 90 seconds. VRMaster statements stop after 30 seconds (the account's own limit, repeated in the transaction), locks after 5 seconds, the client gives up after 35 seconds, connections after 5 seconds, and an aborted turn ends its connection. With `Tudo`, both sources run in parallel within the same deadline. Agent acceptance returns immediately and its browser polls actual progress. The legacy sales route overrides the foundation socket inactivity timeout to 95 seconds, while other routes retain their existing budget. Real ERP queries exceeded the original 10-second round-trip limit, so the bounded budgets now accommodate the measured workload. Limits are process-local, not a distributed quota.

## Local execution and external verification

Follow [setup](../setup.md#sales-chat) and the generated [configuration reference](../generated/configuration/api.md). Oracle node-oracledb 7 supports Oracle 12.1 in Thin mode; if an actual authentication/network feature requires Thick mode, configure a compatible Oracle Client directory. Client 19 or 21 supports this database version; newer clients are not automatically compatible with older servers ([driver compatibility matrix](https://node-oracledb.readthedocs.io/en/stable/user_guide/installation.html)). The account must have CREATE SESSION and SELECT only on the reference tables, with schema resolution supplied by the DBA. No login/provider or real ERP account is provisioned by this repository.

The 2026-10-01 read-only audit connected to Oracle 12.1.0.2 with Client 19.32 after the configured Client 11.2 failed with DPI-1050 and Thin mode failed with NJS-116. Nine structured-query scenarios matched the supplied SQL's aggregates in a shared read-only snapshot: monthly net value, month to date, rolling 30-day weight, quantity by unit, product breakdown, previous year, equal-length prior period, accent/case equivalence, and no matching sales. The complete 46-column reference projection also matched for the current three-month product scope. Returns and bonus movements were present in the source and excluded by the final sales filter. Actual HTTP injection with the real Oracle adapter passed annual comparison and empty-result handling using a controlled planner; this is not a live natural-language test.

The audit exposed unrelated description-prefix matches, a comparison product list exceeding the original cap, and Oracle work exceeding the original timeout. Word boundaries now exclude unrelated prefixes, both periods contribute to the product list, limits reject truncation, and eligible-control pruning reduces work while retaining the reference projection. Oracle response shape/numeric checks reject malformed results rather than inventing empty sales. Small fetch batches in this legacy Oracle/Thick stack produced an intermittent difference in one complete record, although database-side MINUS in both directions returned no differences and aggregates matched. Fetching the complete bounded result together matched every field; the adapter now aligns its fetch array size with each result cap. This workaround does not establish the precise driver/server cause, which remains a DBA investigation under PH-08.

No business totals, credentials, or connection descriptor are committed as evidence. The owner later configured a key manually and explicitly authorized reuse. Ten actual language requests, eight original-SQL reconciliations, and a real-browser sales query passed; see [live verification](../project/live-sales-verification.md). Synthetic tests remain distinct evidence. The supplied account also has broad write privileges, which the DBA must remove by providing a dedicated reader. Weight-unit and currency confirmation remain owner actions.

Boundary tests use the real OpenAI SDK with synthetic HTTP responses and Oracle connection doubles. API injection tests exercise actual Fastify authorization, context, validation, and error envelopes. Browser journeys exercise the generated SDK with intercepted synthetic sales responses, while the unavailable-configuration path reaches the real emitted API. These checks do not replace validation against Oracle 12.1 or a live model. Run the full [validation gate](../validation.md) before handoff. On the real ERP, compare at least an adjusted item, a bonus exclusion, a return exclusion, multiple adjustment joins, accented descriptions, mixed units, missing weight, month end, and both comparison periods against the reference. No verification operation writes ERP data.

### VRMaster

Set the `VRMASTER_DB_*` settings of the [setup](../setup.md#sales-chat) with the dedicated read-only account of [PH-19](../project/human-actions.md#ph-19) (`CONNECT`, `USAGE` on `public`, `SELECT` only on the nine reference tables, `default_transaction_read_only = on`, 30-second statement timeout); never the PDT Connect account. On 2026-10-07 the VRMaster server answered the PostgreSQL TLS request negatively, so its connection needs `VRMASTER_DB_SSL_MODE=disable`, which sends the credentials and sales data unencrypted on that network; the default `verify-full` refuses to connect without TLS. Without VRMaster settings, selecting it reports the source as not configured.

The adapter's tests run the fixed SQL on PostgreSQL 16 with a synthetic VRMaster schema and the PH-19 grants: period totals and inclusive dates, monthly and product grouping, accent- and case-insensitive whole-word product phrases, comparisons, packaging-type quantities, every reference join (excluded and included rows), bound text that looks like SQL or a regular expression, no transaction left open, cancellation of a blocked read and unavailable or refused connections. They establish the transcription's behavior, not agreement with the real VRMaster; that is the reconciliation of [PH-20](../project/human-actions.md#ph-20), with the queries in [VRMaster reconciliation](../project/vrmaster-reconciliation.md).
