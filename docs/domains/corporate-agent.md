# IA-MNS Corporate Agent

## Product and current capabilities

IA-MNS is MNS's corporate AI agent. Its product identity and conversational experience are independent of its first business capability. It can greet users, respond to thanks/wellbeing/identity questions, explain current capabilities and route requests. The only implemented business capability is sales consultation in MNS (Sankhya) and Pilar da Terra (VR Master), chosen with the interface's source selector: net value, quantity and weight (Sankhya only); period/product breakdowns and bounded comparisons ([sources](sales-chat.md#sources)). Purchases, catalog-only product lookup, stock, production, orders, automation and external writes are unavailable. Planned capabilities never appear as available in the catalog.

Social and capability replies are application-authored Portuguese prose selected by a validated bounded intent. OpenAI does not author business numbers, suggest unregistered tools, answer company questions from general knowledge or compose unsupported factual claims. This deliberately limits arbitrary general conversation while allowing a natural social opening without requiring sales details. The UI welcome describes the agent; examples come from registered capabilities. Operational details live in documentation/errors rather than the ordinary conversation shell.

## Implemented architecture

`apps/api/src/features/agent/` owns conversations, routing, persistence, progress and HTTP operations. `features/sales/` retains business semantics, strict interpretation, deterministic results, the source orchestration and one adapter per source (Oracle for Sankhya, PostgreSQL for VRMaster). `apps/api/src/modules.ts` injects configured capability executors into the agent; shared runtime files remain module-independent. The agent and legacy sales transport share one owned sales executor and its source pools. The agent references the sales result contract for its current renderable output, while sales implements the agent's execution interface. This intentional boundary does not grant either module mutation authority over the other's tables.

A capability descriptor has a stable id, localized title/description/examples, required permission, executor and resource cleanup. Only configured implementations enter the catalog. General routing instructions serialize the catalog automatically. To add a future capability, implement its owned bounded tools/context/authorization/tests, provide an executor/descriptor, register it at composition, and extend the public versioned result contract and web renderer if necessary. No general prompt rewrite is required. New domains/actions still need actual product authorization and their own safety/idempotency decisions; a registry entry alone cannot implement them.

The route classifier emits a registered capability id or an allowlisted social/unavailable intent. It emits no user-visible prose. It sees the application's earlier replies and which capability awaits an answer; a message it marks unavailable while a permitted capability awaits an answer is offered to that capability, whose own boundary rejects unsupported requests. A sales request then uses the sales interpreter and its deterministic conversation state machine ([AI interpretation](../architecture/ai-interpretation.md)). `runAgentTurn` performs this orchestration independently of persistence, so evaluation runs the same code. User input/history are untrusted data; fixed application policy and schemas govern execution. Mixed supported/unsupported requests are not partially answered. The capability permission is checked before execution, and reading stored business answers checks current capability permission as well as ownership.

## Persistent conversations and context

PostgreSQL/Prisma owns `agent_conversations` and `agent_turns`; [generated schema](../generated/database/schema.md) records fields, constraints and classification. Conversations have verified owner identity, a bounded editable title (initially derived from the first message), favorite/archive flags, ordering and versioned per-capability context. Turns contain one question, the sales source selected in the interface when it was sent (`sankhya`, `vrmaster` or `all`; earlier turns are `sankhya`, the only source then), client acceptance UUID, ordered sequence, lifecycle state, bounded progress events and a versioned reply snapshot. Reply version 2 holds sales results as one section per queried source; version 1 replies (one Sankhya result) are upgraded when read. No infrastructure credential is stored in these tables.

One turn is accepted at a time under a row lock, without holding a transaction across OpenAI/Oracle work. Acceptance saves the question before starting bounded process-local execution. Replaying the same request UUID, message and source returns the existing turn; a different message or source conflicts. The capability receives the turn's source; the router does not use it. No chargeable provider request is automatically retried. A 120-second database-clock lease handles crashes: stale work becomes interrupted when read or reclaimed, without automatic execution. The process deadline is 90 seconds. Shutdown aborts work and awaits cleanup. This is not a durable workflow engine or an authorization model for future external writes.

Routing uses at most 12 recent completed exchanges: user questions and the application's own replies, with business answers reduced to an "answer delivered" marker, plus the agent context (version 2) naming the capability that awaits an answer. Each capability owns its context version. Sales context version 2 holds structured conversation state: the last executed plan and query, an unanswered request with what it already knows and awaits, and the last 12 sales exchanges, independently of intervening social turns; version 1 contexts upgrade on read. Failed/interrupted turns cannot replace trusted context. Relative periods in a new question use current Sao Paulo time; a follow-up preserves stored explicit filters unless changed. Stored result snapshots are historical answers, not a claim that the ERP remains unchanged. Financial result rows and response prose are never fed back to OpenAI; only questions, application-authored clarification and unavailable messages, filter-only analysis descriptions and structured state are sent. Social turns do not erase sales context or an unanswered sales request.

The generated SDK supports creation, owner-scoped keyset history pages (30), detail pages (40 turns), acceptance, explicit metadata assignment, search and deletion. Active, pinned and archived views belong to the URL via `view`; pinned conversations come first, then modification time and id. Cursor boundaries include the same ordering and filter, preventing cross-filter reuse. Manual titles survive the first turn and are never routing instructions. Rename, pin/unpin, archive/restore and deletion use ownership checks and the same row lock; active execution blocks metadata changes. Archiving preserves messages, answers, favorite state and capability context, and rejects new turns until restored. An already accepted turn can still be replayed while archived. Search uses a bounded, case-insensitive literal substring over owned titles and sent questions, including archives; it does not call OpenAI or search financial result payloads. Search terms and filter-bound cursors use a POST body, not URLs. Search is not accent-insensitive or a semantic/full-text index. The selected conversation id belongs to `/chat/:conversationId`; reloading or opening a previous conversation retrieves PostgreSQL history. Older messages/conversations load in bounded pages. New conversation opens a blank workspace and preserves existing history. Explicit deletion confirms the user's choice and hard-deletes the conversation, context and turns via cascade; active execution blocks deletion.

No prior temporary transcript is migrated: the old UI/process memory had no durable source. Legacy `/sales/chat` endpoints retain their existing temporary semantics for compatibility; the product uses only `/agent` operations. The original numerical/provider tests continue to protect sales behavior.

## Progress and presentation

Progress records are emitted immediately before actual operations: understanding the message (routing), preparing a sales query (sales interpretation), consulting sales (the controlled Oracle operation), and organizing results (validated aggregation). A clarification/social/unavailable reply never claims an Oracle phase. Product identification is part of the Oracle query, so there is no fictional separate product-search step. The browser polls persisted progress about once per second while a turn is running; completed/failed history remains recoverable after reload. The latest real stage is displayed with completed stages beneath it. There are no simulated timers or artificial delays.

The Portuguese agent workspace fills the window without the documentation header, outer page margins or a surrounding card. A compact header owns only the agent identity and mobile drawer control. The sidebar owns new conversation, search, pinned/archived views, documentation, theme selection and each conversation's menu (rename, pin/unpin, archive/restore, delete). Desktop history animates between its adjustable column and a 60-pixel icon rail. Drag the right edge or focus its separator and use arrow keys/Home/End to resize between 240 and 420 pixels, additionally limited to 45% of the window; double-click resets to 260 pixels. Expansion and width remain in the in-memory agent session across conversation navigation. On compact screens, history opens in a native modal drawer with focus containment, Escape/backdrop dismissal and focus restoration. Opening history does not resize the underlying chat. The thread and sidebar history scroll independently; the composer stays visible at the bottom and grows with input up to a bounded height. Message/result and composer columns can use up to 1120 pixels, keeping notebook space useful and wide screens readable.

A native `Fonte` selector sits directly above the message box with `MNS (Sankhya)`, `Pilar da Terra (VR Master)` and `Tudo`. It starts at `MNS (Sankhya)`, keeps the choice in the in-memory agent session across conversations, is never written to browser storage, and is disabled only while an unconfirmed submission awaits verification, which replays its own source. Sales turns show the source they were sent with, and a sales answer shows one group per source, headed `Fonte: …`, with its own totals or the reason it has none; `Tudo` answers state that values are not summed.

The workspace keeps sales tables, matched products, decimal/currency formatting, scope, warnings and comparison inspection. Business caveats such as unverified weight units remain beside relevant results. The conversation, results and documentation share the original light/dark semantic palettes from `apps/web/src/styles.css`; the workspace does not override their colors. The initial theme is light, whatever the OS preference; an explicit choice persists only `light`/`dark` under `ia-mns-theme`. Inside PDT Connect the theme follows the PDT's own light/dark choice through the host bridge and the agent offers no theme control there ([identity](identity.md)). Tokens, sidebar state and confidential transcripts remain out of browser storage, logs and URLs. Token changes and workspace unmount clear owned query caches. Reduced-motion preferences disable sidebar/drawer transitions, progress pulsing and smooth scrolling.

## Local lifecycle, privacy and limits

All questions, titles, context and results are CONFIDENTIAL; credentials are RESTRICTED. Local history persists in the named Docker volume until the owner deletes it. Automatic retention, backups/restoration and provider-copy deletion are not implemented. [PH-09](../project/human-actions.md#ph-09) requires a retention/backup/provider policy before shared deployment. Deletion clears live application data and browser query caches; it does not promise erasure of provider copies or future backups. API responses use no-store and telemetry contains only safe correlated diagnostics, never question/result bodies or arbitrary exception text. The default AI trace level logs one content-free `ai_turn_traced` event per turn; the optional content level stores confidential interpretation traces in `agent_turn_traces`, deleted with the conversation and refused in production until PH-09 ([AI tracing](../architecture/ai-interpretation.md#ai-tracing-and-observability)).

Normal credential-free local access remains explicit, loopback-only and forbidden in production. The separate [phone test](../setup.md#phone-testing-on-the-local-network) requires an expiring bearer and an owner-selected private interface; it maps to the same local owner and does not establish employee identity. It represents one local developer, not multiple employee accounts. Normal bearer ownership uses Orion's verifier with tokens issued by the [identity module](identity.md): the owner is the Person UUID, the same for local, PDT Connect and Sankhya sign-in and for every surface, and `sales:read` comes from the identity permission policy. Tenancy and shared hosting remain outside this module. The Oracle SELECT-only account and currency/weight confirmation remain [PH-08](../project/human-actions.md#ph-08). The application maintains read-only Oracle transactions regardless; PostgreSQL writes are confined to its own history.

## Verification

The owning agent tests use migrated PostgreSQL with restricted grants for restart persistence, concurrency, replay/conflict, interrupted leases, favorite paging, literal search, archive/restore context, owned metadata, cascade deletion and safe failures. Provider schema tests reject invented capabilities/prose and incomplete output. Turn-orchestration tests cover pending-request routing and figure-free router transcripts; integration tests cover content traces, their cascade deletion and capture; the curated [evaluation dataset](../architecture/ai-evaluation.md) replays multi-turn behavior in the ordinary gate. Browser journeys cover the generated SDK, truthful progress, historical navigation/reload, result views, unknown acceptance, credentials, desktop/mobile themes and accessibility. Local real-provider and full-gate evidence is recorded in the project plan; synthetic checks are never described as real ERP reconciliation.
