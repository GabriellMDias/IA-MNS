# IA-MNS

IA-MNS is MNS's corporate AI agent, built on the [Orion](https://github.com/GabriellMDias/Orion) engineering foundation. It provides a Portuguese conversation workspace with persistent history. The conversational assistant can explain, summarize and rewrite authorized evidence, or plan validated read-only analysis through registered tools; it never presents planned capabilities as available. Two business domains are implemented: sales consultation over MNS (Sankhya) and Pilar da Terra (VRMaster), as chosen in a source selector beside the message box, where the two sources are always shown separately and never summed; and product lookup, which identifies matching products through verified ERP-specific dimensions in VR Master and Sankhya ([Sankhya scope and credential requirements](docs/domains/sankhya-product-lookup.md)). [Corporate agent](docs/domains/corporate-agent.md) owns the product direction; [sales semantics](docs/domains/sales-chat.md) and [product lookup](docs/domains/product-lookup.md) retain the business guarantees.

The default [conversational mode](docs/architecture/conversational-autonomy.md) composes reviewed sales metrics and month/product dimensions through the existing Semantic Product Resolver, supports bounded operational text/image attachments and explicit presentation preferences, and applies [controlled business-data transmission](docs/security/ai-data-processing.md). The server retains authority over permissions, ERP scope, calculations and execution; no free SQL or ERP write tool is exposed.

## Current state

ERP access follows the owner-approved [two-user topology](docs/security/erp-database-access.md): one runtime reader and the existing administrator also used for read-only Discovery. Administrative credentials are delivered separately from runtime; The current reader grants are [verified](docs/project/runtime-access-verification.md); PH-08 retains business confirmations and PH-30 tracks inherited VRMaster PUBLIC DDL privileges.

This repository was initialized on 2026-10-01 from Orion commit `53bcc705a9f68f01aa1bbea3a0f4df4a009577ea`. It retains the foundation's architecture, policies, tooling, CI, generated references, and [Living Documentation Portal](apps/web/README.md#living-documentation-portal). It composes the corporate agent and sales modules, PostgreSQL conversation persistence, grounded social responses, actual execution progress, and light/dark themes. Existing deterministic sales results and read-only Oracle access remain in place; a second read-only source reads Pilar da Terra sales from VRMaster PostgreSQL with the owner's reference SQL ([ADR-0027](docs/adr/0027-select-the-sales-source-in-the-interface-and-read-each-source-separately.md)), validated on synthetic PostgreSQL while its reconciliation against the real VRMaster awaits the owner. Product lookup resolves Portuguese requests through machine-readable VR Master and Sankhya semantic catalogs, discovered read-only and verified against live metadata before use: the model chooses among catalog dimensions and real classification candidates, while the application resolves records, compiles parameterized read-only SQL and explains each relationship used ([ADR-0032](docs/adr/0032-resolve-product-selections-through-a-verified-semantic-catalog.md), [semantic product resolution](docs/architecture/semantic-product-resolution.md)); per-store status and a few other dimensions await column grants and owner confirmations. Sales interpretation keeps structured conversation state, so answers to clarification questions complete the pending request; curated multi-turn evaluation cases gate every change, and live-model evaluation, trace capture and synthetic scenarios are opt-in tools ([AI interpretation](docs/architecture/ai-interpretation.md), [AI evaluation](docs/architecture/ai-evaluation.md)). [Local setup](docs/setup.md#corporate-agent-and-local-postgresql) provisions Docker PostgreSQL and starts the application. Live OpenAI/Oracle interpretation and original-SQL reconciliation passed on 2026-10-01 using the existing owner-authorized key; [verification](docs/project/live-sales-verification.md) records the earlier provider repair. IA-MNS has its own identity ([identity](docs/domains/identity.md)): one Person per individual, reachable through an IA-MNS account (password and authenticator app), PDT Connect or Sankhya, with the same conversations and permissions whether opened directly or embedded in PDT Connect or the Sankhya Om. People who use PDT Connect or Sankhya get their profile automatically at first access; there is no public account creation, and owners create and associate everyone else. Permissions are per source, each with a code people give support (for example SNK-VEN-01 for MNS sales, VRM-VEN-01 for Pilar da Terra sales); owners grant them to people or to groups and can restrict sales to real ERP records such as companies, projects, sellers, product groups, stores, buyers, cost centers or classifications, enforced in the reviewed sales queries; when a request needs a permission the person lacks, the agent names the codes to request ([ADR-0037](docs/adr/0037-grant-identified-per-source-permissions-to-people-and-groups-with-data-restrictions.md), [authorization](docs/domains/identity.md#authorization)); restriction by Sankhya result center awaits a reader grant ([PH-36](docs/project/human-actions.md#ph-36)). Owners also administer the operational parameters (AI model, AI trace level and WhatsApp switch) and the default user group joined after verified sign-in through PDT Connect or Sankhya in **Administração → Parâmetros**, which take effect without a restart; secrets and bootstrap configuration stay in the environment ([ADR-0028](docs/adr/0028-administer-operational-parameters-separately-from-secrets-and-bootstrap-configuration.md)). Integration work follows the order direct access, Sankhya, then PDT Connect. IA-MNS reaches the Om through a thin Sankhya add-on in [`apps/sankhya-addon`](apps/sankhya-addon/README.md) that hosts the same frontend and proves the signed-in Sankhya user ([ADR-0026](docs/adr/0026-host-ia-mns-in-sankhya-om-through-an-in-repository-add-on.md)); in the Sankhya development Om, a signed-in Om user already opens IA-MNS from the Om menu without another sign-in and is provisioned automatically at first access. Production publication still awaits review, key custody and the Om security hardening (production refuses Sankhya sign-in until approved). PDT Connect hosts IA-MNS the same way through an IA-MNS screen in the PDT Connect repository, validated with a local PDT; its HTTPS homologation is pending. WhatsApp is a fourth way in ([ADR-0036](docs/adr/0036-add-whatsapp-as-an-agent-channel-authorized-by-owner-linked-numbers.md), proposed): Meta's official Cloud API on a dedicated corporate number reaches the same agent, permissions and history, and only people whose number an owner linked in administration can use it; unknown numbers are ignored silently ([WhatsApp channel](docs/domains/whatsapp-channel.md)). It is implemented and tested with synthetic Meta traffic and a local simulator; the Meta account, number registration, credentials, webhook and approval are owner actions ([PH-32 to PH-35](docs/project/human-actions.md#ph-32)), and the channel stays off until an owner turns it on. For production, the emitted API serves the web build at one origin with the API under `/api`, trusts only enumerated reverse proxies, can listen with internal TLS, and ships compiled operational commands for the owner bootstrap, identity keys, configuration checks and database deployment ([ADR-0029](docs/adr/0029-serve-the-web-and-api-from-one-origin-behind-restricted-trusted-proxies.md)); releases will be `ia-mns-vX.Y.Z` tags ([ADR-0030](docs/adr/0030-name-ia-mns-releases-with-product-tags-distinct-from-orion.md)). Production runs on one Ubuntu host with Docker Compose through the `ia-mns-deploy` tool in [`infra/production`](infra/production/README.md) ([ADR-0031](docs/adr/0031-deploy-on-one-ubuntu-host-with-docker-compose-and-a-release-tool.md)): verified release tags, a private PostgreSQL with separate administrator, migration and runtime roles, pre-deployment and daily backups with restore verification, and rollback only when proven safe; CI rehearses the complete installation with synthetic configuration. Nothing has been installed on the production host yet ([PH-26](docs/project/human-actions.md#ph-26)). The dedicated Oracle reader access is now verified; unit confirmation, inherited PostgreSQL PUBLIC privilege review, production deployment and shared-deployment lifecycle remain owner actions. Application capabilities perform no ERP business writes; separately authorized provisioning tools manage the reviewed Runtime grants. The repository is published at https://github.com/GabriellMDias/IA-MNS. Its `main` branch requires pull requests and the `Orion required gate` check, Renovate is enabled, and the applicable GitHub security controls are on.
